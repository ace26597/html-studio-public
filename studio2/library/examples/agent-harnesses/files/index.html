Explainer · Agent engineering

How AI agent harnesses work, and how to build your own

Prepared 11 November 2026 · Covers Claude Code / Claude Agent SDK, OpenAI Codex CLI, oh-my-pi (OMP) and Pi, plus running any harness on Claude, DeepSeek or other models

In short: a large language model can only read text and write text. A harness is the program wrapped around it that turns this into an agent. It builds the prompt, hands the model a list of tools, runs the tools the model asks for (reading files, running shell commands), feeds the results back, and repeats until the model stops asking. Claude Code, Codex and OMP all run this same loop. Where they differ is in the extras: which tools they offer, how they keep the conversation inside the context window, how much they lock down, and which model APIs they can talk to. You can build a working harness in a few hundred lines. The hard parts are managing context, keeping it safe, and coping with each provider's quirks.

1. What a harness is

The model on its own has no hands. DeepSeek's documentation puts it plainly: “The model itself does not execute specific functions.” [13] The model only writes a structured request, something like “please call read_file with path=auth.ts”. Some other program has to run it and send back the result. That program is the harness.

Think of the model as a brilliant consultant on the phone. The harness is the assistant in the office: it reads documents aloud, runs errands, refuses dangerous ones, and keeps notes so the consultant doesn't lose track.

Anthropic separates workflows, where LLMs and tools are “orchestrated through predefined code paths”, from agents, which are systems where “LLMs dynamically direct their own processes and tool usage” [5]. A coding harness falls in the second group: the model decides which tool to call next, and the harness carries it out.

Also note that the API server keeps no memory between calls. As the Amp tutorial says, “the server … is stateless. It only sees what's in the conversation slice. It's up to us to maintain that.” [8] So on every turn the harness sends the whole conversation again.

2. The agent loop: the heart of every harness

Claude Code, Codex and OMP all run the same cycle. Anthropic's Agent SDK documentation describes it in five steps [2]: receive the prompt, let the model evaluate and respond, execute any tools it requested, repeat, and return a result once the model “produces a response with no tool calls”. OpenAI describes the Codex loop the same way: “If a tool call is requested, the agent executes it, appends the output to the prompt, and re-queries the model.” [10]

Guardrails live inside the loop. The Claude Agent SDK lets your code intercept every tool call with hooks. Hooks run in your application process, not inside the agent's context window, and “a PreToolUse hook that rejects a tool call prevents it from executing, and Claude receives the rejection message instead” [2]. Limits like max_turns and max_budget_usd keep open-ended tasks from running forever [2].

3. What actually gets sent to the model

Every API call carries a full “context” built by the harness. OpenAI's write-up of Codex lists the pieces. The request uses three main Responses API parameters: instructions, tools (shell tool, plan tool, web search, and MCP server tools) and input. Input holds permission messages, developer instructions, user instructions gathered from AGENTS.md files and skills, environment context such as the working directory and shell, and finally the user's message [10].

Why the order matters: prompt caching. Providers can reuse computation for a prompt prefix they have already seen. So Codex makes sure “each new prompt is an exact prefix extension of the previous one, so only the new tokens need processing” [10]. The cache breaks when “tools change order, the model changes, or sandbox configuration is modified mid-conversation”. A good harness therefore keeps its tool list in a fixed order and appends new information rather than editing old messages.

How big should the system prompt be? Opinions differ. Pi's author argues that frontier models already “understand what a coding agent is”, so there is no need for “10,000 tokens of system prompt”. Pi runs with just four tools: read, write, edit and bash [6]. Larger harnesses like Claude Code and OMP put many more tools and instructions up front to get more behaviour out of the box.

4. Context, compaction and memory

The context window is the model's whole working memory, and tool output fills it fast. The Claude docs warn that “reading a big file or running a command with verbose output can use thousands of tokens in a single turn” [2]. Harnesses deal with this in three ways:

  • Compaction. When the window “approaches its limit, the SDK automatically compacts the conversation: it summarizes older history to free space” [2]. Codex does the same: when usage crosses auto_compact_limit it calls a dedicated /responses/compact endpoint [10].
  • Re-injected rule files. Compaction can drop early instructions, so the Claude docs say persistent rules belong in CLAUDE.md, “because CLAUDE.md content is re-injected on every request” [2]. Codex reads AGENTS.md in the same way [10].
  • Progress files for long jobs. For work that spans many context windows, Anthropic used an “initializer agent” that sets up an init.sh script and a claude-progress.txt file, plus a feature list of over 200 features all marked failing. Every later session reads these files and git history to pick up where the last one stopped [11].

Tool definitions cost context as well. Pi's author measured that Playwright MCP (21 tools, 13.7k tokens) and Chrome DevTools MCP (26 tools, 18k tokens) load their full tool descriptions into every session [6]. That is why newer harnesses lean on “progressive disclosure”: they show the model a short summary first and load the details only when needed.

The security trade-off is real. Pi's author argues that “as soon as your agent can write code and run code, it's pretty much game over” for in-process safety checks [6]. Codex and Claude Code instead add sandboxes and permission layers. If you build your own, choose deliberately: run in a container or VM, or add permission gates.

6. Swapping models: Claude, DeepSeek and others

This is the part most people ask about. A harness talks to a model over HTTP, so changing the model mostly means changing three settings: the base URL, the API key and the model name. The hard part is that providers speak slightly different dialects.

Route A: point an existing harness at another model

DeepSeek publishes an Anthropic-compatible endpoint. Its docs say you can set ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic along with your DeepSeek key, and they link a guide for using DeepSeek inside Claude Code [4]. Model names are mapped: names starting with claude-opus go to deepseek-v4-pro, and Sonnet/Haiku names go to deepseek-flash [4].

# Example: run Claude Code against DeepSeek (per DeepSeek's docs)
export ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic
export ANTHROPIC_API_KEY=sk-...your-deepseek-key...
claude

“Compatible” rarely means identical. DeepSeek's own table shows several Anthropic fields are ignored, for example cache_control on tools is ignored, and tool_choice: any is “treated as auto; does not force a tool call” [4]. Features that depend on those fields can behave differently.

Route B: a multi-provider harness

OMP and Pi are built from the start to talk to many providers. Pi's pi-ai library wraps every provider behind one interface. Even so, its author lists quirks it has to patch around: some providers want max_tokens instead of max_completion_tokens, some reject the developer role, and reasoning arrives in different fields [6]. Token and cost reporting is inconsistent too. He calls it “the Wild West”.

The thing every adapter must get right: tool-call round-trips

Each dialect has strict rules for sending tool results back. For DeepSeek's Anthropic endpoint, “the immediately following message must have the user role and include a tool_result for every tool call, with matching tool_use_id values”. With thinking mode on, you must pass the model's full content back, including its thinking blocks [4]. In the OpenAI-style format the result goes in a message with role: "tool" and a tool_call_id [13]. Getting this bookkeeping wrong is the most common reason a custom harness breaks when you switch models.

7. Building your own harness

Anthropic's advice is to “start by using LLM APIs directly: many patterns can be implemented in a few lines of code” [5]. Here is a path from zero to something useful.

  1. Chat loop. Keep a messages list, append the user's input, call the API, append the reply, print it. Because the server is stateless, you resend the whole list every time.
  2. Define tools. Give each tool a name, a one-line description and a JSON schema for its inputs. Start with read_file, list_files, edit_file and bash, the same core set Pi uses.
  3. Inner tool loop. If the reply has tool calls, run each one, append the results with matching IDs, and call the model again. Stop when the reply is plain text. This is the agent.
  4. Safety. Add an allow/deny check before every tool runs (a hook), a turn cap and a spend cap. Run inside a container or VM if the agent can execute shell commands.
  5. Context management. Truncate huge tool outputs. When token usage nears the limit, ask the model to summarise older turns and replace them with the summary. Load a project rules file (AGENTS.md) into every request.
  6. Provider adapters. Keep one internal message format and write a small translator per API dialect. Make base URL, key and model name configuration, so switching from Claude to DeepSeek is a config change.
  7. Polish. Add streaming output, saved sessions (JSONL logs), MCP or CLI tools, subagents and a nicer UI. Or skip all this and build on an SDK such as the Claude Agent SDK, which gives you “the same execution loop that powers Claude Code” [2].

A minimal harness in Python (works with DeepSeek, OpenAI, Ollama, OpenRouter…)

Illustrative code written for this explainer, using the OpenAI-compatible Chat Completions format that DeepSeek documents [13]. Change BASE_URL and MODEL to switch providers. It has no sandbox, so run it only in a throwaway folder or container.

import json, os, subprocess
from openai import OpenAI          # pip install openai

BASE_URL = os.getenv("LLM_BASE_URL", "https://api.deepseek.com")   # or http://localhost:11434/v1 for Ollama
MODEL    = os.getenv("LLM_MODEL",    "deepseek-flash")
client   = OpenAI(base_url=BASE_URL, api_key=os.environ["LLM_API_KEY"])

# 1) Tools: name + description + JSON schema. The model only *requests* these.
TOOLS = [
  {"type": "function", "function": {"name": "read_file", "description": "Read a text file",
     "parameters": {"type": "object", "properties": {"path": {"type": "string"}}, "required": ["path"]}}},
  {"type": "function", "function": {"name": "write_file", "description": "Create or overwrite a file",
     "parameters": {"type": "object", "properties": {"path": {"type": "string"}, "content": {"type": "string"}},
                    "required": ["path", "content"]}}},
  {"type": "function", "function": {"name": "bash", "description": "Run a shell command, return output",
     "parameters": {"type": "object", "properties": {"cmd": {"type": "string"}}, "required": ["cmd"]}}},
]

def run_tool(name, args):
    # 2) Guardrail: the harness decides what is allowed.
    if name == "bash" and any(bad in args["cmd"] for bad in ["rm -rf", "sudo"]):
        return "DENIED by harness policy"
    if name == "read_file":  return open(args["path"]).read()[:20_000]      # truncate big outputs
    if name == "write_file": open(args["path"], "w").write(args["content"]); return "ok"
    if name == "bash":
        r = subprocess.run(args["cmd"], shell=True, capture_output=True, text=True, timeout=60)
        return (r.stdout + r.stderr)[-20_000:]

rules = open("AGENTS.md").read() if os.path.exists("AGENTS.md") else ""
messages = [{"role": "system", "content": "You are a coding agent. Use tools to act.\n" + rules}]

while True:                                          # outer loop: one user task per pass
    messages.append({"role": "user", "content": input("you> ")})
    for turn in range(30):                           # inner agent loop with a turn cap
        reply = client.chat.completions.create(model=MODEL, messages=messages, tools=TOOLS).choices[0].message
        messages.append(reply)                       # keep the assistant turn (incl. tool_calls)
        if not reply.tool_calls:                     # no tool calls -> task done
            print("agent>", reply.content); break
        for call in reply.tool_calls:                # run every requested tool
            out = run_tool(call.function.name, json.loads(call.function.arguments))
            print(f"  [{call.function.name}] {str(out)[:120]}")
            messages.append({"role": "tool", "tool_call_id": call.id, "content": str(out)})

That is a real, working agent. Everything Claude Code, Codex and OMP add on top (sandboxes, compaction, diff-based edits, subagents, LSP, session files, UIs, prompt caching discipline) is what turns the toy into a dependable tool. The Amp tutorial [8] builds the same thing step by step in Go against Claude, and is the best hands-on next step.
